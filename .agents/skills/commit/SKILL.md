# 커밋 규칙

## 1. 변경 내용 파악

커밋 메시지를 쓰기 전에 실제로 무엇이 바뀌었는지 확인한다.

```bash
git status
git diff --staged   # 스테이징된 게 없으면 git diff
```

`git log --oneline -10` 으로 최근 커밋들의 문체도 함께 확인한다.

## 2. 관련 이슈 번호 찾기

이 저장소의 브랜치명에는 이슈 번호가 들어가지 않는다(`feature/DungeonGenerate`).
따라서 **항상 이슈 목록을 조회해서** 번호를 찾아야 한다.

1. 열린 이슈를 조회한다.
   ```bash
   gh issue list --state open --limit 30
   ```
2. 브랜치명과 변경 내용을 이슈 제목과 대조한다. 제목만으로 애매하면
   `gh issue view <번호>` 로 본문을 확인한다.
3. **후보가 여러 개거나 확신이 없으면 추측하지 말고** 후보 2~3개를 사용자에게
   보여주고 어느 이슈인지 물어본다.
4. 맞는 이슈가 하나도 없으면 번호 없이 커밋한다. **없는 번호를 지어내지 않는다.**
5. 한 브랜치에서 여러 번 커밋할 때, 앞선 커밋에서 이미 이슈를 확정했다면
   (`git log --oneline -5` 로 확인) 다시 조회하지 말고 그 번호를 재사용한다.

## 3. 메시지 형식

제목은 수행한 작업의 한 줄 요약이고, 맨 뒤에 이슈 번호를 붙인다.
본문은 주요 변경사항을 번호 목록으로 나열한다.

```
플레이어 점프 구현 및 콜라이더 사이즈 조정 #123

1. PlayerController 점프 로직 추가
2. Movable 인터페이스를 상속하여 플레이어 이동 구현
```

규칙:

- 제목은 한국어, 기존 히스토리와 같은 명사형 종결 (`~구현`, `~수정`, `~조정`)
- 제목 끝 이슈 번호 앞에는 공백 하나. 괄호로 감싸지 않는다.
- 이슈가 여러 개면 `... 구현 #123 #124`
- 본문은 `1.` `2.` `3.` 번호 목록. 변경사항이 하나뿐이면 본문을 생략해도 된다.
- 본문 각 항목은 "어떤 파일/클래스에 무엇을 했는지"가 드러나게 쓴다.
  "버그 수정" 같은 뭉뚱그린 표현 금지.
- 이슈를 이 커밋으로 닫아야 하면 본문 마지막 줄에 `Closes #123` 을 추가한다.

여러 줄 메시지는 heredoc으로 전달한다.

```bash
git commit -m "$(cat <<'EOF'
플레이어 점프 구현 및 콜라이더 사이즈 조정 #123

1. PlayerController 점프 로직 추가
2. Movable 인터페이스를 상속하여 플레이어 이동 구현
EOF
)"
```

## 4. 지켜야 할 것

- `master` 브랜치에 직접 커밋하지 않는다. 현재 브랜치가 `master`면 먼저 브랜치를 판다.
- `--no-verify` 로 훅을 건너뛰지 않는다. 훅이 실패하면 원인을 고친다.
- 사용자가 요청하지 않았으면 커밋만 하고 push는 하지 않는다.
- 커밋 후 `git log -1` 로 메시지가 의도대로 들어갔는지 확인한다.

## 5. Unity 프로젝트 주의사항

- `.meta` 파일은 대응하는 에셋과 **같은 커밋**에 포함시킨다. 하나만 커밋되면
  다른 팀원 쪽에서 참조가 깨진다.
- `Library/`, `Temp/`, `Logs/`, `Build/` 가 스테이징에 올라와 있으면 커밋하기 전에
  사용자에게 알린다.
